<objective>
Fix two session routing bugs in runner-service.ts:
1. Fix 1: Add a guard in `triggerNewSession` so pi (capture.mode: "off" + create.mode: "explicit") routes directly to `restartRunnerWithFreshSessionIdForNewCommand` instead of `triggerNewSessionInLiveRunner`. The live-runner path calls `captureNewSessionIdentityAfterTrigger` with `forceStatusCommand: true`, which bypasses the capture.mode: "off" guard and hangs waiting for a `/status` command that pi does not have.
2. Fix 2: Widen the gate in `retryFreshStartAfterStoredResumeFailure` to allow `create.mode: "explicit"` alongside `create.mode: "runner"`. Currently the gate returns null for pi, silently discarding the stored session ID on crash recovery.

Purpose: Make `/new` work for pi without timeout errors; make crash recovery preserve pi session IDs.

```typescript
async triggerNewSession(target: AgentSessionTarget) {
  const resolved = this.resolveTarget(target)
  // Pi uses explicit session IDs with no capture command; cannot rotate in-process.
  // Route directly to restart with a fresh UUID rather than triggering live rotation,
  // which would call captureNewSessionIdentityAfterTrigger (requires /status — pi has none).
  const skipLiveRotation =
    resolved.runner.sessionId.capture.mode === 'off' &&
    resolved.runner.sessionId.create.mode === 'explicit'
  if (skipLiveRotation) {
    return this.restartRunnerWithFreshSessionIdForNewCommand(target)
  }
  if (!(await this.tmux.hasSession(resolved.sessionName))) {
    return this.restartRunnerWithFreshSessionIdForNewCommand(target)
  }
  return this.triggerNewSessionInLiveRunner(resolved)
}
```
